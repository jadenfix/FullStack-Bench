# INC-3187: support pages timing out during the Friday peak

**Impact.** 14:05 to 14:31 UTC. Agents could not open customer pages (`GET /customers/<id>` returned
503 "database busy" after about two seconds); `/healthz` stayed green the whole time, so the load
balancer kept routing to both instances. Reports for the new mobile app had launched the same
morning with a 400 ms render deadline.

**What we saw.** `/admin/pool` on both instances showed every permit in use, most owners
`report:<request id>` with ages of several minutes. On the database, `pg_stat_activity` listed the
same number of sessions `idle in transaction`, each with an open `report_...` cursor. The mobile
app's requests had all ended with 504 within half a second.

**Mitigation.** Restarted both instances at 14:29; pages recovered within a minute. Nobody wants to
raise `POOL_MAX`: the managed Postgres is shared with billing and its connection budget is fixed.

**Follow-up.** Find why a report that ends early keeps its connection, fix it before the next peak,
and prove it with the mobile client's own cancellation pattern. Owner: on call.
